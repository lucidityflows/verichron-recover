# `gateways` Feature Module

## 1. Overview

The `gateways` module is a critical infrastructure module within the `api-transactions` microservice. It is responsible for isolating and abstracting all interactions with third-party payment providers (e.g., Stripe).

Its primary purpose is to provide a unified, provider-agnostic interface for processing payments and refunds, and to securely handle asynchronous notifications from these gateways via webhooks. This module acts as the final bridge between the application's internal business logic and the external financial processing services.

---

## 2. Ownership & Boundaries

### What This Module Owns

-   **Gateway Communication Logic:** It is the single source of truth for all API calls to external payment providers.
-   **Provider Abstraction:** It owns the `GatewaysService` facade and the provider-specific implementations (e.g., `StripeService`) that allow the rest of the application to remain agnostic to the specific payment gateway being used.
-   **Webhook Endpoints:** It owns the `GatewaysController`, which exposes endpoints to receive webhook events from payment providers.
-   **Webhook Security:** It is responsible for verifying the authenticity of all incoming webhook requests (e.g., Stripe signature verification) to prevent spoofing.
-   **Idempotency and Retry Logic:** It manages idempotency keys and implements retry mechanisms for transient network errors to ensure payment operations are safe and reliable.

### What This Module Does NOT Own

-   **Business Logic:** It does not contain any business logic related to payment plans or transactions. It only executes the commands given to it by the `transactions` service.
-   **Database Entities:** This module is stateless and does not own any database entities.
-   **Payment Initiation:** It does not expose endpoints for initiating payments directly. All payment operations must be started through the `transactions` module, which then calls this module's services.
-   **User Context:** It has no awareness of users or organizations; it operates on the specific payment details it is given.

---

## 3. Endpoints

This module does not define any database entities. It exposes a single webhook endpoint for each integrated provider.

### `POST /gateways/stripe/webhooks`

-   **Description:** A webhook endpoint that receives and processes asynchronous events from Stripe. This is crucial for receiving notifications that cannot be handled in a single synchronous request, such as chargebacks.
-   **Headers:**
    -   `stripe-signature` (string, **required**): The signature generated by Stripe, used to verify the authenticity of the request.
-   **Permissions:** This endpoint is public-facing but secured by mandatory signature verification. Unsigned or incorrectly signed requests are rejected with a `401 Unauthorized` status.
-   **Key Handled Events:**
    -   `charge.succeeded`: Confirms a payment was successful (provides redundancy).
    -   `charge.failed`: Confirms a payment failed (provides redundancy).
    -   `charge.dispute.created`: A critical event indicating a customer has initiated a chargeback.
-   **Responses:**
    -   `200 OK`: If the webhook is received and verified successfully.
    -   `401 Unauthorized`: If the `stripe-signature` header is missing or invalid.

## 4. Key Concepts & Patterns

### Facade Pattern (`GatewaysService`)

The `GatewaysService` acts as a facade, providing a simple, unified interface (`processPayment`, `processRefund`) to the more complex underlying system of multiple payment providers. The `transactions` module interacts only with this facade, decoupling it from the specific implementation details of Stripe or any future provider.

### Provider Abstraction (`IPaymentProvider`)

The `StripeService` implements the `IPaymentProvider` contract (defined in `@verichron/contracts`). This design pattern ensures that all payment providers adhere to a standard interface. Adding a new provider (e.g., PayPal) is as simple as creating a new service that implements this interface, making the system highly extensible.

### Webhook Security

The `POST /gateways/stripe/webhooks` endpoint is a security-critical component. It uses `stripe.webhooks.constructEvent` to verify that every incoming request is genuinely from Stripe and has not been tampered with. This check uses a secret key (`STRIPE_WEBHOOK_SECRET`) and the `stripe-signature` header, and it is mandatory for processing any event. Failure to verify results in an immediate `WebhookVerificationFailedException`.

### Idempotency and Retry Logic

-   **Idempotency:** All charge and refund operations require an `idempotencyKey`. This key is passed to the Stripe API to prevent accidental duplicate operations that could result from network retries or other transient issues.
-   **Retry Mechanism:** The `StripeService` includes a private `executeWithRetry` method that wraps all API calls. It uses an exponential backoff strategy to automatically retry operations that fail due to transient network errors (e.g., 502, 503), enhancing the system's resilience. It does **not** retry on terminal failures like a card decline.

### Custom Exceptions

The module defines specific exceptions for clear error handling:
-   `GatewayException` (500): A general-purpose exception for when a gateway operation fails for a technical reason.
-   `WebhookVerificationFailedException` (401): Thrown specifically when a webhook signature is invalid, indicating a potential security issue.

---

## 5. Events

This module does not publish or subscribe to any internal domain events via the GCP Pub/Sub message bus. Its primary event-driven interaction is consuming external events from payment providers via HTTP webhooks.

---

## 6. Dependencies & Integrations

### Internal Dependencies

-   **`@verichron/contracts`:** Provides shared interfaces like `IPaymentProvider` and `GatewayResponse` that define the contract between this module and the rest of the application.
-   **`@verichron/error-handling`:** Provides the `BaseException` class for creating custom, standardized exceptions.
-   **Note:** This module has no direct dependencies on other modules within `api-transactions`. It is a foundational layer that is injected into other modules (primarily `transactions`).

### External Integrations

-   **Stripe:** The primary external integration. The module connects directly to the Stripe API to process payments, handle refunds, and verify webhooks.
-   **`stripe` (Node.js library):** The official Stripe SDK used for all API communication.
-   **GCP Secret Manager (Implicit):** The module requires `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` to be securely provided as environment variables at runtime.

---

## 7. Gaps & Future Work

-   **Hardcoded Provider Selection:** The `GatewaysService` currently hardcodes the payment provider as 'STRIPE'. A future enhancement is to make this dynamic, allowing the provider to be selected based on organization-specific settings fetched from `api-organizations`.
-   **Incomplete Webhook Handlers:** The logic within the webhook handlers (`handleChargeSucceeded`, `handleChargeFailed`, `handleDisputeCreated`) is currently limited to logging. These handlers need to be fully implemented with database logic to update transaction statuses, create incident records for chargebacks, and provide redundancy for the synchronous flow.
-   **Single Provider Implementation:** While the architecture is designed to support multiple providers, only `StripeService` is implemented. Future work involves adding services for other gateways like Plaid or PayPal.
-   **Limited Webhook Event Coverage:** The controller only handles a few legacy Stripe events (e.g., `charge.succeeded`). It should be updated to handle more modern events from the Payment Intents API (e.g., `payment_intent.succeeded`) and refund events for more comprehensive tracking.
